# CHANGES

This file is the release changelog, with one `## <version> - <title>` entry per release, newest first. The Cursor-to-T3 rewrite rules live in [`tools/substitutions.json`](tools/substitutions.json), and the [sync boundary](CONTRIBUTING.md#the-sync-boundary) in `CONTRIBUTING.md` defines how a change to upstream's skill content is declared.

## 2.0.0 - t3-pstack 2.0: Lauren's pstack, rewritten for T3

2.0.0 is 2.0.0-rc.19 under its final version, with no change to any skill, script, or hooks file. The 2.0 line rebuilds t3-pstack on Lauren Tan's pstack at cursor/plugins, now at `e73df47` (pstack 0.15.32), with Cursor-specific text rewritten in place for T3 on Claude Code and Codex. The release candidates rc.1 to rc.19 below record each step. From here on, each sync of Lauren's pstack ships as a patch or minor release under semantic versioning, as [`CONTRIBUTING.md`](CONTRIBUTING.md#releasing) describes, and each release gets a GitHub release with its entry as notes.

## 2.0.0-rc.7 - Worktree cleanup keeps ignored files, scratch, and reflog-only commits

Worktree cleanup could destroy work that existed nowhere else, as [cursor/plugins#449](https://github.com/cursor/plugins/issues/449) reports. The audit bucketed a worktree `safe` when it held only untracked scratch or an ignored file such as `.env` or `.claude/settings.local.json`. Step 5 then ran `git worktree remove --force`, and `rm -rf` on any directory that survived. A commit that only the worktree's HEAD reflog reached, such as one made on a detached HEAD, went with the worktree too. Removal deletes that reflog and leaves the commit for `git gc`. The audit also called itself read-only, yet it fetched the base ref ([cursor/plugins#470](https://github.com/cursor/plugins/issues/470)), and its `git status` rewrote the index of each worktree it read. That write can collide with an agent working in the worktree.

The audit now asks `git status` for ignored paths with `--ignored=matching`. It counts each one whose last component is not in a named list of build and cache directories, such as `node_modules`, `.venv`, `__pycache__`, `dist`, `build`, and `target`, as `ignored:N` and holds the worktree as `hold-ignored`. The audit walks each worktree's HEAD and HEAD reflog and counts commits that no branch, tag, remote, or branch reflog reaches as `reflog:N`, held as `hold-reflog`. HEAD itself is in the walk, so a detached commit still counts after `git gc` expires its reflog. A branch reflog lives in the shared logs and outlives the worktree, so a rebased branch's old tip does not count. Both checks port Michael Denyer's [pstack-claude #277](https://github.com/michael-denyer/pstack-claude/pull/277) from his JavaScript audit to Lauren's bash script, with his test cases. Untracked scratch now holds as `hold-scratch`, and an explicit `--untracked-files` keeps a `status.showUntrackedFiles=no` config from hiding it. A worktree git cannot read holds as `unknown` instead of reading `clean`. The audit fetches only under `--fetch` and sets `GIT_OPTIONAL_LOCKS=0`, so without `--fetch` it writes nothing to the repository.

## 1.0.13 - reflect finds its own Claude and Codex transcripts

Reflect's step 1 now finds this conversation's own transcript on a Claude Code thread, with the default config home or a redirected one, and on a Codex thread with any `CODEX_HOME`. Before, a redirected Claude home and every Codex thread fell back to a digest the parent wrote, and a Claude thread could pick a sibling session that shared its opening prompt. The Codex resolver comes from Eric Litman's open-pstack [PR #151](https://github.com/ericlitman/open-pstack/pull/151) (issue #140), which builds on Donncha O'Toole's tested candidate. t3-pstack modifies it as listed below, and `NOTICE.md` records the changes beside their credit.

- **Claude session ID.** Claude Code 2.1.296 exports the session's ID to every shell command as `CLAUDE_CODE_SESSION_ID` and names the transcript after it. Step 1's command passes it to `find-transcript.mjs --session`, which prints `<id>.jsonl` or `<id>/<id>.jsonl` from the projects directory when one exists, with no prompt to compare. When the variable names no file, as under Claude Code's `--no-session-persistence`, which exports the ID and writes no transcript, the finder exits 1 and step 1 passes the digest. The fragment scan runs only when the variable is unset. A `delegate_task` child, a forked session, or a restarted one sits in the same projects directory and often has the same opening prompt, so the scan's newest match could be any of them. An `Agent` subagent's shell sees its parent's ID, so the ID names the parent conversation's file, never one under `subagents/`.
- **Claude config home.** Step 1's command reads `"${CLAUDE_CONFIG_DIR:-$HOME/.claude}/projects/<encoded-cwd>"`, so a thread whose provider instance sets `CLAUDE_CONFIG_DIR`, such as a pool at `~/.claude_pool`, searches its own home instead of `~/.claude`. It still searches only that one per-project directory. The command quotes the plugin path, which failed with `MODULE_NOT_FOUND` when the install path held a space. Tests in `tests/find-transcript.test.mjs` run the command as the skill gives it, from a plugin path with a space, against a redirected home, the default home, and siblings that share the session's opening prompt, including a session with no file of its own.
- **Codex resolver.** `skills/poteto-mode/scripts/resolve-codex-transcript.ts` and its `sh` launcher come from open-pstack at `c5c8e23`. The launcher is unchanged and runs the resolver under `bun --no-env-file --config=/dev/null`, so a project's `bunfig.toml` or `.env` cannot change the lookup. The resolver looks up one chat ID in the `threads` table of Codex's index, read-only, checks that the rollout is under `$CODEX_HOME/sessions/` and belongs to the chat, and prints its path, never its text. Its 26 tests are ported to `tests/resolve-codex-transcript.test.mjs`, which now holds 29 that cover the changes below. Prettier now formats the file, so `.prettierignore` no longer lists it.
- **Index directory (modified).** The resolver finds the index directory as Codex 0.162.1 does: `sqlite_home` in the home's `config.toml`, relative to the home, else `CODEX_SQLITE_HOME`, else the home. Both expand a leading `~`. It reads only `$CODEX_HOME/config.toml`, not `/etc/codex/config.toml`, a project's `.codex/config.toml`, a profile, or a `-c` override, so a `sqlite_home` set only there ends in `index_missing` and the digest. Rollouts must still be under `$CODEX_HOME/sessions/`.
- **Relative `CODEX_SQLITE_HOME` (modified).** Codex reads a relative `CODEX_SQLITE_HOME` against its own working directory at startup, which a shell command cannot know, so the resolver fails it as `sqlite_home_relative` instead of reading it against its own working directory. An absolute or `~` path works as before.
- **Index version (modified).** It uses the newest `state_<n>.sqlite` that opens with the `threads` schema. Before, two indexes failed the lookup as `index_ambiguous`, and an unreadable one failed it as `index_unreadable`, even an older file that a Codex upgrade left behind.

## 1.0.5 - watch-pr holds READY until review activity settles

An audit of agent babysitting history found that the most common failure, about 121 of 227 flaw instances, was declaring a PR ready once CI turned green but before review bots such as Codex, CodeRabbit, Devin, or Bugbot had posted. `watch-pr` knew only Bugbot.

- `watch-pr` has a review settle window, `--settle <seconds>` (default 300, `0` disables it). READY waits until no account other than the PR author and the `gh` viewer has commented, reviewed, review-commented, or reacted on the PR body or a comment for that long. A create or an edit counts, because some bots edit their comments. Anything that activity raises, such as a review thread, still goes through the existing checks. The rule names no bot.
- The window starts at the latest of the head's push, the PR's opening, and its last ready for review, since bots start on each of these. The push time comes from the head repository's activity log (`GET /repos/{owner}/{repo}/activity`) when its newest entry for the head branch moved the branch to the head commit. Commit dates are not used, because a rebase pushed later keeps its old dates. A head with no such entry, or a log the viewer cannot read (HTTP 403 or 404), starts the window when the watcher process first sees the head, and a push time read earlier for the same head is kept. Any other failure of that read retries like any other GitHub read.
- An `eyes` reaction from another account, added at or after the start, holds READY until 30 minutes after the start (`EYES_HOLD_CAP_SECONDS`). After that cap, only the quiet rule applies.
- While the window is open, the watcher waits with the new `review-settling` reason, which carries `endsAt` and `heldBy` (`activity` or `eyes`). In the bounded drive loop that is one more `TIMEOUT`, so the existing rule to run the watcher again covers it. Each open `--status-only` row carries its `settle` state, and the table's Review cell shows how long the window has left. Queued mode does not settle, since it only watches a verified stack land. The draft, review-required, and branch-protection gates already wait for pending checks, and they now wait for the window too, so a bot's review threads come before a hand-off to a human reviewer.
- Issue comments are read newest-updated first, so an edit to an old summary comment counts on a PR with many comments. Reviews and review threads are read as the newest 100 created, so an edit deep in an older thread on a very long PR can go unseen. The read asks GraphQL for `viewer`, so the watcher needs a user token, as `gh` on a T3 host has. Two gaps remain: without a push record each new watcher process starts its own window, so an eyes reaction from before that process does not hold it, and reopening a PR does not restart the window.
- `t3-tools.md` says that the standalone `babysit` skill's own polling (`gh pr checks --watch`, the `loop` skill) is replaced on T3 by the Babysit mapping, and that the watcher's settle window means no per-bot rules are needed.

The logic, its types, and its GitHub reads live in the new port-only `watch-pr/settle.ts`. These files from pstack-claude carry an overlay hook to keep in a merge: `types.ts` (a type import from `settle.ts`, the `settle` field on open snapshots, the `SettleWait` wait reason, the `reviewActivity` reader method, `PollingOptions.settle`), `policy.ts` (`readSnapshot` reads the settle state, `waitReason` falls through to `settleWait`, `runSimple` builds the settler), `github.ts` (`GhGitHubReader.reviewActivity` delegates to `readReviewActivity`), `render.ts` (the Review cell suffix and the WAITING and TIMEOUT text), and `cli.ts` (`--settle`). The tests that build `PollingOptions` (`cli.test.ts`, `policy.test.ts`, `integrity.test.ts`), the fake reader (`fakes.test-helper.ts`), and the fake `gh` in `transport.test.ts` carry matching one-line additions.

## 0.9.9 - principle leaves hide from the slash menu

0.9.8 kept `disable-model-invocation: true` on the 20 `principle-*` leaves, on the reasoning that they have no command and are read by path from `poteto-mode`. But that flag only blocks *model* invocation. It does not hide a skill from the user `/` menu, so all 20 surfaced as bare `/principle-*` slash commands in every session (confirmed across projects on the desktop app). They are internal references; users should never invoke them.

Fix: swap the flag for `user-invocable: false` on all 20 leaves. Per the [Claude Code skills docs](https://code.claude.com/docs/en/skills.md), `user-invocable: false` hides a skill from the `/` menu and controls menu visibility only, not Skill-tool or file access — so `poteto-mode` reading each leaf by path (`../principle-<name>/SKILL.md`, the mechanism the leaves have always used) is untouched. The two flags are mutually exclusive: setting both leaves a skill neither user- nor model-invocable, so this is a swap, not an addition. The visible consequence is that the leaves become model-auto-invocable on description match — the same standing the 12 command-paired skills took in 0.9.8, and immaterial to the by-path reference the leaves actually rely on. The invariant is now: every command carries `disable-model-invocation: true`, no command-paired skill carries it, and every `principle-*` leaf carries `user-invocable: false`.

`tests/skill-collision-repro.sh` gains the mirrored static invariant (no skill with a same-named command may carry the flag) and a fourth behavioral leg preserving the repro: with the flag on the skill, the Skill tool refuses the invocation even though the command no longer shadows it.

## 0.9.7 - command trampolines no longer shadow their skills

Every user-facing skill ships with a same-named `commands/<name>.md` trampoline whose body is "Invoke the `<name>` skill and follow it." On Claude Code, the Skill tool resolves a colliding name to the **command**, not the skill — so a model-initiated invoke of `pstack:<name>` got the trampoline back, which told it to invoke the skill, which resolved to the trampoline again. Mutual recursion; the real `SKILL.md` never loaded. This hit every model-side entry path, including the 0.9.5 SessionStart mandate (whose whole job is telling the model to invoke `pstack:poteto-mode`), and it made each name appear twice in the model's skill list. Observed in desktop-app sessions (inline `--plugin-dir` loading, same path as the 0.9.3 entry); reproduced on CLI 2.1.195 with a minimal two-artifact plugin.

Fix: all 24 command files now carry `disable-model-invocation: true` — the flag the `principle-*` leaf skills already use. Verified on 2.1.195 with the same minimal plugin: the Skill tool then resolves the colliding name to the skill (its `SKILL.md` is what gets injected), while a user-typed `/plugin:<name>` still runs the command trampoline, whose "invoke the skill" body now lands on the skill instead of looping. Command bodies are unchanged, so the Codex prompts path (which reads `description` frontmatter and the filename, and ignores keys it doesn't know — the established `name`-key precedent) is untouched. Whether a full Codex plugin install still surfaces the stubs in its picker with the flag present is unverified; if it hides them, the skills themselves remain the primary Codex surface and are invocable by name. Incidental finding from the same repro, recorded for future use: `${CLAUDE_PLUGIN_ROOT}` **is** substituted inside command markdown bodies on 2.1.195, not just in hooks and MCP configs.

The repro is preserved as `tests/skill-collision-repro.sh` (manual; needs the `claude` CLI, makes three haiku calls). It checks the static invariant (every command carries the flag) and the three behavioral legs: command wins the collision without the flag, skill wins with it, user-typed `/command` still runs. The first leg is a precedence detector — if it ever fails, upstream changed the undocumented resolution order and the flag should be re-evaluated, not the fix declared broken.

## 0.9.5 - poteto-mode auto-fires via SessionStart hook

## 0.9.3 - dependency declaration removed

`plugin.json` no longer declares `dependencies: [{ "name": "plugin-dev", "marketplace": "claude-plugins-official" }]`, and `marketplace.json` drops the matching `allowCrossMarketplaceDependenciesOn`. The Claude Code desktop app passes every enabled plugin to the CLI as a session-only `--plugin-dir`, which strips marketplace identity (`pstack@inline`); a cross-marketplace dependency can never resolve in that mode, and the loader disables the entire plugin with `dependency-unsatisfied`. Result: pstack loaded in the CLI and the VS Code extension but silently vanished from desktop-app sessions. `optional: true` on a dependency entry passes `claude plugin validate` but is not honored by the loader (tested on 2.1.197). `plugin-dev` is now a documented manual install (README → Dependencies); skill bodies still route skill-authoring to `plugin-dev:skill-development` when it is present.
